Run the benchmark for your task on your machine

A benchmarkable task is currently a completed Hive coding task in 9-done with a merged GitHub pull request. The merged PR becomes a held-out reference; candidates receive the task inputs but never that patch. If the task is still in flight or has no merged reference, finish it before benchmarking it.

You need Docker, Ruby 3.4, a Hive release that includes the built-in bench workflow, authenticated agent CLIs for the candidates and judges you select, and enough provider quota for full planning, implementation, PR, review, and judging runs.

1. Select Hive's built-in benchmark workflow

git clone https://github.com/ivankuznetsov/hive-bench.git
cd hive-bench
bundle install
hive init . --workflow bench

bench is a named workflow packaged with Hive. Its descriptor and stage instructions do not need to be copied into .hive-state. It runs through the normal Hive daemon, locking, ordering, and concurrency controls; Honeycomb is not required.

2. Extract your completed task into your local corpus

ruby -I harness harness/extract.rb \
  --task-dir /absolute/project/.hive-state/stages/9-done/<task-slug> \
  --repo owner/repository \
  --repo-path /absolute/project \
  --out corpus

This creates corpus/<task-slug> from the frozen task materials and merged PR. Keep that corpus entry local if the task is private. The benchmark runner itself isolates the candidate from reference.patch.

3. Pre-register and run a campaign

hive new <hive-bench-project> "benchmark my task"
hive status

The project default selected by hive init routes this task to bench. For an existing Hive project with another default, use hive new <project> --workflow bench "benchmark my task". In the new task folder reported by hive status, copy campaign.yml.example to campaign.yml. Set a new campaign id, the absolute source-repository path, your corpus task slug, candidate ids, exact judges and reasoning effort, sample count, timeout, budget declaration, and any exclusions. Then commit the file inside the state worktree: 

cp campaign.yml.example \
  .hive-state/stages/1-inbox/<campaign-slug>/campaign.yml
$EDITOR .hive-state/stages/1-inbox/<campaign-slug>/campaign.yml
git -C .hive-state add stages/1-inbox/<campaign-slug>/campaign.yml
git -C .hive-state commit -m "Pre-register benchmark campaign"

Do not amend the campaign after a model run has spent tokens; start a new campaign instead. The supplied example matches the maintained follow-up method: Fable 5 plus GPT-5.6 Sol at ultra, three independent samples per judge and cell. For a private smoke comparison, reduce the task/candidate matrix deliberately before the first run. 

hive approve <campaign-slug>
hive run <campaign-slug>

# After each COMPLETE stage, advance and run the next stage:
hive approve <campaign-slug>
hive run <campaign-slug>

You can instead enroll the project in the Hive daemon and let normal Hive dispatch, locking, retry, and per-project concurrency rules drive the stages. One campaign task runs its matrix in stable serial order; independent campaign tasks can run concurrently within Hive's configured limits. Results land at runs/<campaign-id>/results.json and the publish stage renders its summary.

See the benchmark workflow reference, the available candidate profiles, and Hive's custom-workflow guide.

Submit a task to the public Hive benchmark

Public submission adds a reusable task to the corpus; it does not run paid model cells or immediately change the leaderboard. Once the entry is reviewed and merged, maintainers can include it in a later pre-registered public campaign.

Before invoking the command, remember that the task idea, brainstorm, plan, provenance, and merged reference diff will become public. Check the completed task for confidential material first. The task must be in 9-done, contain worktree.yml and pr.md, belong to a registered Hive project with a GitHub origin, and point to a merged reference PR.

1. Prepare a fork checkout

# Fork ivankuznetsov/hive-bench on GitHub, then:
git clone https://github.com/<you>/hive-bench.git ~/Dev/hive-bench
export HIVE_BENCH_PATH=~/Dev/hive-bench
gh auth status

2. Extract and open the submission PR

hive bench submit <task-slug>

# If the same slug exists in more than one registered project:
hive bench submit <task-slug> --project <project-name>

Hive reuses hive-bench's extractor, runs a local pattern-based scan over the task spec for credentials and private hostnames, creates a submission branch, pushes it, and opens the pull request. The public validator then checks structure and provenance, candidate-visible answer leakage, secrets across the complete entry, and reference reproducibility.

Validation of contributor code begins only after a maintainer applies safe-to-validate. It runs on the pull-request commit with a read-only GitHub token, no repository secrets, and an isolated benchmark runner. Start at the hive-bench repository if you want to inspect the corpus schema or validator before submitting.
