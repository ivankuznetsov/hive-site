hive-bench v2

Which AI model ships real software best?

Hive is an open-source autonomous development pipeline: you give it a task idea, and AI agents carry it through brainstorm → plan → implementation → pull request → code review, end to end. Which AI model should drive that pipeline? That is the question hive-bench answers — with evidence instead of vibes.

Why measure this

Most coding benchmarks test models on isolated puzzles. But when an agent pipeline does the work, the model isn't solving a puzzle — it has to scope a fuzzy idea, plan, implement across a real codebase, open a PR, and survive code review. Whether a model can carry a whole workflow is a different question from whether it can pass a unit test, and it's the question that actually decides which model you configure your tooling with.

What is measured

We take six real tasks that were already completed in the hive repository — each with a human-merged pull request as ground truth — rewind the codebase to just before each task was done, and let a candidate (the pipeline configured with a specific model, e.g. all-Opus, all-GPT, all-GLM, or a mixed pair) run the entire pipeline on it, in an isolated container, with no access to the original solution. The candidate's final post-review diff is then compared against the PR a human actually merged.

How it is scored

  1. Two blind judges (gpt-5.5-pro and fable-5) each grade the diff 0–10 on an absolute rubric — "does this correctly and completely accomplish the task?" — with the merged PR as a reference signal, not an answer key to match.
  2. No self-grading: a judge that shares a model family with a candidate never counts toward that candidate's headline score.
  3. Verified, not trusted: every run's logs are checked to confirm the claimed model actually ran, and judges must survive a cross-examination round where they fact-check each other's verdicts against the diff.

What we found

No single winner — three different frontiers. codex (gpt-5.5) is the reliability frontier: it finished every task without a single failure, but never excelled on hard ones. opus-4.8 is the capability frontier: the only model to score above the floor on the hardest task (install packaging, 4.0 vs everyone else's 2.0) — but its subscription limits made it the hardest candidate to even run. glm-5.2 is the value frontier: near-codex quality, fully pay-per-token, with the board's best single result. And mixing models (one plans, another implements) works for the closed pair but reproducibly broke for the open one — a handoff is its own risk.

Example: one task through the pipeline

Task fix-tmux: "Fix two issues running Hive with Claude Code in tmux mode" — a real bug a human fixed in PR #623. Each candidate got the original idea and brainstorm, planned its own fix, implemented it, opened a (sandboxed) PR, and ran hive's review loop. The all-GLM candidate produced a 400-line diff that both judges scored 8.0–9.0 — it found both root causes and shipped tests. Codex scored 7.0/7.0 with a correct but shallower fix. On the same task the open glm→kimi pair failed to produce a diff at all: the handoff between planner and implementer broke — which is itself a result.
