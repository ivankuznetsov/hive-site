hive-bench v2

Which model should drive an autonomous dev pipeline?

Hive is an open-source autonomous development pipeline: you hand it a task idea, and LLM agents carry it through brainstorm → plan → implementation → pull request → code review. I run it daily, so at some point I had to decide which model to put behind it. hive-bench is how I decided: replay tasks I already merged through the real pipeline under different models, and grade what each one ships.

Why measure this at all?

Public coding benchmarks score models on isolated problems with a known pass condition. Inside a pipeline the model faces different work: scope a fuzzy idea, write a plan, implement it across a live codebase, open a PR, then survive code review of its own change. A model can be strong on the first kind of work and mediocre at the second — and only the second tells me what to put in hive's config.

What is measured

The corpus is six real tasks from the hive repository, each already finished and merged as a pull request. That merged PR is the ground truth, and I'm the one who merged it.

A candidate is what gets measured: hive configured with one model for every stage, or with a mixed pair, where one model writes the plan and a different model implements it. The mixed pairs matter later — one of the board's findings is about them.

For each task, the repo is rewound to the commit the original work started from, and the candidate runs the full cycle in an isolated container: plan, execute, open a sandboxed PR, run hive's production review. It never sees the reference solution. What gets graded is its final, post-review diff.

How it is scored

  1. Two blind judges (gpt-5.5-pro and fable-5) grade each diff independently, 0–10 on an absolute rubric: does this accomplish the task? They see the merged PR as a signal of what the task needed; a candidate is never scored on how closely it matches it, and verbosity is explicitly not rewarded.
  2. One ranking per judge, never mixed: the two judges score on visibly different scales — fable-5 runs 1–2 points more generous — so each judge gets its own full table and scores from different judges are never combined into one column. An external review of this benchmark's design caught that an earlier mixed presentation compared rulers instead of candidates; the current tables fix it. Rows where a judge shares a model family with the candidate stay in the table but carry a same-family flag.
  3. Model claims are audited: every cell's logs are checked to confirm the claimed model actually ran — 101 substantive stage logs, 0 violations.
  4. Judges cross-check each other, as a diagnostic: after scoring independently, they exchange anonymized verdicts and verify each other's claims against the diff. This never moves the headline numbers — the leaderboard keeps the independent scores.

What came out

No candidate wins outright, and the answer depends on which judge you ask — which is itself a finding. Reading each judge's own table:

glm-5.2 is the strongest clean result on the board: it leads both judges' rankings among candidates with no family conflict (gpt 4.0, fable 6.0), completed all six tasks, and runs fully pay-per-token. codex (gpt-5.5) at its default reasoning effort is the reliability pick — six of six tasks, zero stage failures, the cheapest and most token-efficient run — but the strict judge puts its quality at 3.4, at the 2.0 floor on three of the six tasks.

Pinning codex's reasoning to xhigh changed that: all-codex-xhigh tops both judges' quality columns (gpt 4.25, fable 6.5, with the gpt score carrying a same-family flag), lifting the install floor from 2.0 to 3.0 and matching the board's best fix-tmux at 8.0.

opus-4.8 is the capability frontier on hard tasks — the only above-floor install score before xhigh arrived (4.0 where everyone got 2.0) — but subscription limit windows made it the hardest column to even run. kimi-k2.7-code is bimodal: 8.0/8.5 on fix-tmux against 1.0/1.0 on daemon, with a fragility at the execute stage where empty final turns stall hive's stage markers.

A cross-model handoff turned out to be its own failure mode. The open glm→kimi pair reproducibly broke at execute on install and fix-tmux — two funded attempts each — even though each model finishes those stages solo on other tasks. The end-to-end column makes this visible: counting its failures as zeros, the pair drops from a 4.0 quality mean to 1.3.

Send your task to the benchmark

The corpus grows from real, completed hive tasks — and if you run hive, yours qualify. Any task that reached 9-done with a merged PR can become a benchmark entry: 

hive bench submit <task-slug>

The command extracts the task's frozen idea and brainstorm plus the merged PR as the reference, runs a secret/PII scan over the spec before anything leaves your machine (the same scanner the benchmark's own gate uses, so the local check can't be weaker than the one that judges the PR), and opens a pull request against hive-bench. CI then validates the entry in a sandbox — fork PRs run with a read-only token, no secrets, and only after a maintainer applies a safe-to-validate label.

What gets a submission rejected, automatically: reference-solution lines appearing in the candidate-visible spec (if the brainstorm quotes the answer, executing the task collapses to transcription — three of my own tasks were rejected for exactly this), secrets or private hostnames anywhere in the entry, and a reference that fails to reproduce against its own gate. Fresh tasks are especially valuable: a task benchmarked before models could have trained on its PR is the cleanest contamination defense this design has.

One task, end to end

Task fix-tmux: "Fix two issues running Hive with Claude Code in tmux mode" — a real bug a human fixed in PR #623. Each candidate got the original idea and brainstorm, planned its own fix, implemented it, opened a sandboxed PR, and ran hive's review loop. The all-GLM candidate shipped a 429-line diff that the judges scored 8.0 and 9.0 — the best dual-judged cell on the board. Codex earned 7.0 from both judges. The glm→kimi pair never produced a diff here: its execute stage failed on both funded attempts, so its cell reads as an exclusion.
